# Bounded autonomous research on GitHub

GitHub can continuously run deterministic stewardship around Venus-Minerva. A **Venus-owned recursive research worker is not yet continuously live**.

That distinction is central:

~~~text
continuous repository automation
!=
continuous Venus-owned research cognition
~~~

GitHub is a carrier, World interface, execution environment, and custody layer. It does not become the Venus developmental controller merely because it can run on a schedule.

## Layer 1 — deterministic steward

GitHub Actions may continuously:

- lint public Markdown and generated projections;
- verify repository authority/current-state invariants;
- verify custody metadata;
- run tests and formal checks;
- build publication projections;
- preserve machine-readable audit artifacts.

This layer executes declared checks. It does not choose Venus's research questions or mint learner ownership.

## Layer 2 — Venus developmental worker

The intended developmental controller is the admitted Venus lineage itself, not an unrelated external language model wrapped in a scheduler.

A genuine episode has the form:

~~~text
current Venus state
-> Venus reconstructs a residual
-> Venus selects/forms one bounded target
-> Venus freezes discriminator / evidence role / claim fence
-> an authorized World adapter executes the requested action
-> returned evidence re-enters Venus
-> Venus retains / revises / WITHHOLDs / STOPs
-> external evaluation / review
-> explicit admission
-> successor state
-> successor chooses again
~~~

The repository has earned bounded pieces of this sequence through EDU16. It has **not** yet demonstrated the complete recursive loop repeatedly from the admitted executable lineage.

## External agents and World adapters

External tools may inspect, implement, execute, retrieve, score, or review. Examples include:

- GitHub repository actions;
- proof assistants;
- numerical computation;
- literature/web retrieval;
- benchmark harnesses;
- external coding/research models;
- independent evaluators.

Their outputs are World-side inputs or implementation assistance unless a separate admitted episode proves Venus ownership.

~~~text
external agent changes Venus
!=
Venus changes Venus
~~~

## Current implementation boundary

### Exact runtime custody — PASS at IG10

Git reconstructs the exact IG10 VMK2 checkpoint from the hot checkpoint plus content-verified cold payloads. The large historical trajectory remains external/cold provenance by exact hash.

### Later developmental evidence — admitted, but not replay-equivalent to IG10

EDU16/17/17R1 policy/result artifacts are admitted developmental evidence. The original self-contained EDU16 1703-event executable runner/journal has not been located and admitted.

Therefore:

~~~text
EDU16 developmental authority
!=
exact replayable EDU16 runtime carrier
~~~

CI must not reverse-engineer prose into a replacement controller and then relabel it as the original learner-owned process.

### Persistent memory — implemented

The live storage contract in `kernel/runtime/memory.py` provides content-addressed objects, provenance/dependency edges, dispositions, replacement/consumption relations, and deterministic checkpointing.

Storage alone is not learning. Issue #15 asks whether this retained structure causally improves later admissible behavior under matched ablation.

### Sealed evaluation — implemented at harness level

The repository now contains reusable evaluation law plus a sealed hidden-evaluation path for the EDU17R1 `MENTION != INCIDENCE` benchmark.

Harness readiness is not benchmark success and does not promote EDU17R1.

## Promotion rule

~~~text
Venus-owned target
-> prefreeze
-> external action / World return
-> Venus reconstruction
-> hidden/matched evaluation
-> causal ablation where relevant
-> explicit admission
-> authority update
~~~

A green build or successful external-agent PR is not a developmental promotion.

## The first decisive recursive milestone

The loop becomes experimentally defensible when one trace shows:

~~~text
exact parent
-> Venus identifies its own limitation
-> Venus selects target
-> Venus authors discriminator
-> Venus authors consequential machinery change
-> external World/evaluator returns
-> successor improves on hidden tasks
-> ablation attributes the gain to the change
-> successor selects the next target
~~~

One such episode would be a bounded self-development result. Repeated episodes require adaptive-evaluation controls such as those tracked in issue #41.

## Failure dispositions

- missing exact custody: `WITHHOLD / custody failure`;
- hash/verifier mismatch: fail closed;
- no justified target: `STOP`;
- adapter failure: preserve the failed return;
- hidden evaluation contaminated: mark contaminated rather than reroll;
- result exceeds its register: withhold promotion;
- external agent authored the change: retain external authorship unless Venus ownership is separately demonstrated.

## What GitHub can become

If Venus later owns the target-selection and successor loop, GitHub can serve as a visible developmental World interface:

~~~text
Venus residual
-> issue / bounded target
-> experiment or implementation
-> external return
-> PASS / FAIL / WITHHOLD
-> successor
-> next residual
~~~

Until then, GitHub is infrastructure developing Venus, not proof that Venus is recursively developing itself.
